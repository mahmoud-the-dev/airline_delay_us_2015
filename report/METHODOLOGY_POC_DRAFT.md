### a. Data cleaning and preparation

The working file is `raw/Flight_Delays_Cleaned.csv`, 50,000 rows from the 2015 BTS on-time extract in the Kaggle 50k pack. `src/clean.py` writes `clean/flights.parquet`, the dashboard never opens the CSV, and the grain stays one row per scheduled flight.

Arrival delay is blank on every cancelled flight and every diverted flight, 794 and 121 rows, because those flights never completed a scheduled arrival. Clock fields that never happened are blank in the same rows, and we did not impute them, because filling arrival delay would invent a landing time. `OPERATED` is false for cancelled and diverted rows, so `DELAYED` cannot treat a blank `ARRIVAL_DELAY` as late. On operated rows `ARRIVAL_DELAY` has no missing values, the Kaggle pack already filled cause-minute columns with zeros, and we left the remaining columns unchanged.

We called `drop_duplicates` and the row count stayed 50,000, because the extract had no duplicate scheduled-flight rows to remove.

`clean.py` does not recast columns, and pandas infers types from the CSV, so `CANCELLED` and `DIVERTED` come in as booleans, delay minutes as floats, and calendar fields as integers, which parquet then stores. October 2015 stores `ORIGIN_AIRPORT` and `DESTINATION_AIRPORT` as 5-digit BTS airport IDs (4,228 rows); every other month already uses 3-letter IATA. `clean.py` leaves 3-letter codes unchanged and replaces 5-digit IDs from the first sheet of `raw/lookups/BTS_2015_Airport_ID_IATA.xlsx` (322 ID→IATA pairs reconstructed for 2015 from the BTS 2021 historical archive, not a 2015-published lookup). In this extract every October ID matched, so leftover count is 0. If an ID had no match the cell would stay numeric; airport charts would drop those rows only, via `ORIGIN_IS_IATA` / `DEST_IS_IATA`, and would not drop the rest of October.

We added `OPERATED` as not cancelled and not diverted, `DELAYED` as operated and `ARRIVAL_DELAY` at least 15 minutes, and `AIRLINE_NAME` from the two-letter code, keeping the raw code if a name were missing, which never happened in this extract. `DEP_HOUR` is the scheduled departure hour clipped to 0–23, and `TIME_BLOCK` bins that hour as Overnight 0–5, Morning 6–11, Afternoon 12–16, Evening 17–20, and Night 21–23, so BQ3 and BQ5 can group by period without reading the raw clock field. Every row has a block, because scheduled departure is filled even when the flight never left. `DOW_NAME` maps `DAY_OF_WEEK` 1 through 7 to Monday through Sunday. The extract already used that numbering: 2015-01-01 was Thursday, and those 137 rows are 4, so we did not recode the integer, we only added the weekday name. `CANCEL_REASON_NAME` maps `CANCELLATION_REASON` A, B, C, and D to Carrier, Weather, NAS, and Security, and any other value, including blank, to Not cancelled, so we did not recode the letter, we only added the label. `SEASON` maps `MONTH` to DJF, MAM, JJA, and SON, December through February, March through May, June through August, and September through November, so grouping can use meteorological season without reading the month number. `CANCEL_REASON_NAME` maps `CANCELLATION_REASON` A, B, C, and D to Carrier, Weather, NAS, and Security, and any other value, including a blank, to Not cancelled, so we did not recode the letter, we only added the reason name. `SEASON` maps `MONTH` to DJF, MAM, JJA, and SON for December–February, March–May, June–August, and September–November, and we left the month integer unchanged.

No normalization was applied to any column. The stored table stays flight-level, while the app groups operated rows by airline and by month.

### b. Modeling / dashboard design

We structured the table for a filterable BI page. pandas writes the clean table, `dashboard/metrics.py` holds the KPI functions, and Streamlit plus Plotly draw the page, while we froze the definitions in `KPI_DICTIONARY.md` and the page calls `flights`, `delay_rate`, and `avg_delay_minutes` on the filtered frame instead of recomputing those ratios in the layout.

The sidebar has a single filter on airline names. Clearing the list leaves zero rows, so the flights card shows 0 and delay rate and average delay show a dash rather than 0% or 0 min, and Reset is the only control that puts every airline back. Month filters are planned for final.

The page is a single screen with three cards and two delay-rate charts. The Flights card counts filtered rows including cancelled and diverted, the delay-rate card is delayed operated flights divided by operated flights shown to one decimal percent, and avg delay minutes is the mean `ARRIVAL_DELAY` among delayed operated flights only. Both charts use the same operated `DELAYED` mean, so the axis stays 0 to 1 with percent ticks and matches the delay-rate card. Horizontal bars rank airlines with the worst delay rate first, and a line by `MONTH` 1 through 12 keeps January on the left and leaves a gap if a month is empty rather than drawing a slope through missing points. Cancelled and diverted rows stay out of those two charts, and causes, time and risk, and cancel-versus-delay tabs are planned for final.

### c. AI/BI modeling

We did not train a classifier and we did not forecast 2016. `src/clean.py` writes a second table, `clean/delay_risk_bands.parquet`, as a historical BI lookup for BQ5. Operated rows only are grouped by `AIRLINE`, `DAY_OF_WEEK`, and `TIME_BLOCK`, each cell stores `n_flights` and `delay_rate` as the operated `DELAYED` mean, and cells with fewer than 30 operated flights are dropped, because a rate on a thin cell is noise. Remaining rates are banded Low below 15%, Medium from 15% up to but not including 25%, and High at 25% and above. We used those fixed cuts rather than terciles, so the same delay rate keeps the same band if the mix of cells changes. This extract kept 297 of a possible 490 airline–weekday–block cells, 99 Low, 114 Medium, and 84 High. `AIRLINE_NAME` and `DOW_NAME` are copied onto the lookup so a later page does not have to join the name maps again.
